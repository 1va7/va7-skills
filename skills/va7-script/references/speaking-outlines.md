# 口播论证大纲

用于已有方向和素材后的大纲创作，以及把用户口述整理回可审核结构。2026-09-06 根据用户选定的四篇成稿重建；它们是本轮整理的参考，不是历史逐字获批大纲，也不是所有稿件的固定模板。

## 交付标准

让用户能检查“这篇到底在说什么、凭什么成立、哪里需要补充”，并能据此口述或交给agent代写。

- 用普通bullets表达具体内容。主要论证点先给可讨论的判断，再补支持它的必要机制或事实；不能只写“讲激励”“加案例”“认知升级”。
- 保持比全文更低的阅读负担：一条通常以一个简短判断配一两句必要解释即可，复杂处按需展开。不要重复金句、写法说明、目录和成稿句子；不设统一字数或条数。
- 整份大纲要有真实的关系。并列原因、先后阶段、问题回答、方案递进都可用；不用每一条机械填写“观点、机制、案例、转折”。
- 研究可以全面，入稿选择典型。事实来源不足的关键位置单列“待补”，不能填入想象的亲历、数字和产品能力。
- 方向确认与大纲确认不同。审核大纲时同时检查要讲的问题、回答的实质和证据；同一轮完成，不人为增加两轮确认。开头的承诺必须由后文兑现。
- 用户整篇口述带来新的判断时，更新主张和结构，不能只塞回旧分类。已确认的术语、层级、范围及用户撤回的说法随版本更新。

## 自检方式

读完一个主要bullet，能否指出观众多会了什么判断？删掉其中的例子或细节，论证是否还成立？若只留下专业标签、目的复述或“这很重要”，补必要机制；若事实和结论之间还有跳步，明确缺口。

检查整体是否有重复、越界和虚构的因果。案例少而讲透可以有效，多案例对照也可以有效；先看它们分别证明什么，不追求数量。用户没要求计时或固定长度时，不靠凑字数制造深度。

## 参考一：AI 转型中一号位要做哪些事

- **“一号位工程”需要回答两问：懂到什么程度，哪些事必须亲自负责。** 从大家认同的共识切入，再用与创始人、CIO闭门交流的经历引出认知和责任的区分。
- **认知体现在Agent有没有成为默认工作入口。** 对照会议纪要直接进入CRM/SRM、收到QA List却另做Word的工作习惯，落到老板能否判断真实提效、Demo与可完成任务的Loop。
- **定结果要落在业务上。** 工作流和Agent的数量不能直接代表成果；真实使用体感帮助一号位判断哪里能提效、目标应定到哪里。
- **给实权要处理“责任集中、否决分散”。** 中台拖数据、部门不放人、HR不改KPI，会让公开支持失效。负责人要能拿资源、改规则，冲突交一号位裁决并执行。
- **做取舍需要公司整体视角。** AI提效使岗位能覆盖更大范围，组织结构随之需要调整；转型收益归公司，抽走骨干、改岗位和短期业绩波动先落具体部门，这些冲突需要一号位拍板。
- **承担这三项责任后，具体执行交给负责人。** 本篇在认知和ownership处收口，高管选择、业务AI Owner、FDE安排留到下一篇，再接个人结尾。

关系：两问组织全篇，三项责任并列；真实体感支撑合理设定目标。不要编成“做完定结果才发现还需要实权”的三次实验。

## 参考二：FDE 局限性／FDE 搞不定的是什么

- **技术和人的转变需要一起发生。** 与至少100位FDE交流的经历引出边界：系统搭建、流程改造之外，员工是否愿意使用和贡献经验，还取决于激励与人才体系。
- **技术配齐后仍可能几乎没人用。** 200多人的教育公司搭好Agent、知识库和Harness并做培训，一周后人均Token消耗仍不到10元；这个反例引出员工采用的问题。
- **不主动探索可能是员工的理性选择。** 学习、实操和失败补锅先消耗个人时间；成功后成果归公司，个人未必获益，还可能担心被替代。风险收益错配解释了为何工具齐备仍不够。
- **激励同时改变探索收益和失败成本。** 表彰、创新OKR及绩效让成果有回报；学习时间和试点让尝试有空间。不能用旧KPI把额外成本全部留给个人。
- **建设者与使用者需要不同要求。** 用户实践中一个百人团队可能只有十几二十人能沉淀跨团队可用的Skill；其他员工用好这些成果同样有价值，不要求人人成为先锋。
- **人才体系把识别连接到成长与招聘。** 结合岗位指标和Agent日志找到真实先锋，与管理层、HR设计成长路径，再用相应画像招人；部分人才可成长为内部FDE。
- **企业需要承担技术之外的组织工作。** 收束到激励与人才和FDE技术工作的配合；原稿随后接当时的管理层课程内测邀请和个人签名。

关系：一个反例引出激励和人才两个问题，各自说明机制与实践。数字是作者提供的案例和观察，不外推为行业规律；课程邀请是当时结尾用途，复用时另查是否有效。

## 参考三：FDE 不是去找和优化业务瓶颈的

- **先把老板的合理判断讲完整。** 不到50人的电商公司认为美工出图最慢，所以买AIGC、培训和工作流以提高ROI，结果仍一周出一套图；让观众先判断自己是否也会这么选。
- **投入没有解决旧协作中的返工。** 看到“美工慢”便继续加强美工能力，是把AI放进旧流程和旧基础设施。接下来沿同一案例检查两类返工。
- **方向返工来自上游需求未定。** 场景、人物动作和角度还没想清楚，运营就交给美工试，快做完才改变方向。过去运营找不到参考图、不会PS，这种分工有其成因。
- **AI降低试错成本，方向探索可以回到需求提出者。** 运营先出七八十分的草图并确认方向，美工再处理材质、光影和复杂物理交互；从分工源头减少方向返工。
- **细节返工来自规范没有沉淀。** 字体、字号、表格等要求散在聊天和图片批注中，每张图都重新沟通。整理为可供Agent读取的规范、参考资料和参数，才能在生成时提供依据。
- **沉淀以后，还要让反馈更新规范。** 日常批注不应只修当前图片，还应进入知识库、工作流或Skill的更新过程，成为下一次工作的依据。
- **FDE的判断涉及未来的组织与协作方式。** 接受老板对症状的归因便卖培训或Agent，可能继续固化旧问题。以探索新协作方式、把有效的未来带回业务收束，再接个人结尾。

关系：方向返工和细节返工是并列来源；“规范持续更新”才是规范沉淀后的延伸。不要改成需求表失败后才试知识库、知识库失败后才试草图的虚构时间线，也不补回已删的市场指标、岗位撤留支线。

## 参考四：如何防止 Skill 越改越差

- **持续补充Skill，为什么可能“反向进化”？** 先提问题，再用团队每个Agent平均126个Skills的历史实践背景引出版本管理。
- **局部修补可能累积成整体退化。** 客户同类任务从约10轮变成约20轮，员工抱怨Agent变笨；回查日志和修改记录，才有条件判断哪里出了问题。轮次变化本身还不能独立证明原因。
- **效果判断和变化追踪需要配合。** Eval判断效果，版本管理记录改了什么；Eval作为背景，本篇重点展开捕获、审核、统一版本三步。
- **先让改动可见。** 除了人明确要求修改，运行中的自动迭代也可能改动Skill；未同步记录就难以回查。需要捕获追踪范围内的新增、修改、删除，但看见差异还不代表应该收下。
- **审核决定改动能否接受。** 检查差异、原因和风险，有Eval结果时一并作为证据，再接受、驳回或交人判断；不让新文件未经判断就变成正式版本。
- **局部接受还需要共同的版本依据。** A已改过，B仍沿旧版继续，便会产生多个“最新版”。把接受的变更和理由记入Git，建立可追溯的正式版本；具体分发与运行机制另行核实。
- **回扣可见、可判断、可追溯这三个目标。** 交代项目入口和个人结尾，不把版本管理扩成所有Agent工程问题的总解法。

关系：看见改动不等于接受改动，各自接受不等于形成共同版本，三个步骤有真实的缺口衔接。用户保留了这个主干，替换的是生物学铺垫和冗长桥段。

实现边界：历史发布审计发现当时部分Hook/Cron与Eval表述超前于实现，随后用户要求补最小功能。这里将方法和实现分开，不能把本例当作自动执行Eval、自动分发所有设备或自动回滚已完成的证明。数字仅沿用用户的历史实践，未经本轮独立验证。
